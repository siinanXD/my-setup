# Deployment and Secrets

This file defines the default deployment and secret-management convention for projects that follow `docs/ENGINEERING.md` and `docs/AI_ENGINEERING_WORKFLOW.md`.

The goal is simple: a new device should need the repository plus authenticated access to the secret manager — never copied `.env` files, secrets in Git, or manual production configuration drift.

## Source of truth

Use one owner for each kind of state:

| State | Source of truth |
| --- | --- |
| Code, non-secret config, deployment definitions | GitHub |
| User-managed application secrets | Infisical |
| Human account credentials, passkeys, recovery codes | A trusted password manager |
| Vercel/Railway environment variables | Runtime copies synced from Infisical where practical |
| Platform-generated values | The platform that owns them |

Examples of user-managed secrets: `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, webhook signing secrets, third-party API tokens.

Examples of platform-generated values: Railway service references and database connection variables generated by Railway. Do not copy those into Infisical just to force a single-store model when the platform already owns their lifecycle.

## Default deployment architecture

For the standard Next.js + FastAPI stack:

- **GitHub** is the code source of truth.
- **Vercel** hosts Next.js frontend applications.
- **Railway** hosts FastAPI services, workers, scheduled/background processes, and PostgreSQL when managed there.
- Feature branches and pull requests are the review boundary.
- Vercel Preview Deployments are the default UI preview environment.
- A human merge to `main` is the production approval. Platforms may deploy automatically after that merge; coding agents must not run production deploy/promote commands themselves.

Typical flow:

```text
feature branch
  -> CI
  -> Vercel preview when a web app exists
  -> review
  -> human merge to main
  -> automatic Vercel/Railway production deployment
  -> health/smoke verification
```

## Environments

Start with only the environments that are useful:

| Environment | Purpose |
| --- | --- |
| `dev` | Local development and safe developer credentials |
| `preview` | Pull-request / integration previews |
| `prod` | Production only |

Add persistent `staging` only when a real integration, migration, customer acceptance flow, or production-like test requires it.

Never use production credentials locally by default. Development and preview should use separate credentials, databases, buckets, webhook endpoints, and AI limits when side effects or cost matter.

## Infisical convention

Infisical is the default source of truth for **user-managed project secrets**.

Prefer one Infisical project per deployed product/repository. Keep access narrow instead of creating one giant vault that every project can read.

Useful paths inside an Infisical project:

```text
/common
/web
/api
/worker
```

Use the same paths across `dev`, `preview`, and `prod` where possible. Secret names stay stable between environments; values change.

The generated `.infisical.json` contains project linkage, not secret values, and may be committed so every device resolves the same project.

## Local development from any device

Do not synchronize `.env` files through iCloud, Dropbox, Google Drive, chat, notes, or Git.

On a new development device:

1. Clone the GitHub repository.
2. Install the Infisical CLI.
3. Run `infisical login` and authenticate as yourself.
4. If the repo does not already contain `.infisical.json`, run `infisical init` once and commit that non-secret project linkage in a normal PR.
5. Start the application with secrets injected into the process.

Examples:

```bash
# Next.js
infisical run --env=dev --path=/common --path=/web -- npm run dev

# FastAPI
infisical run --env=dev --path=/common --path=/api -- uvicorn app.main:app --reload
```

Prefer process injection over writing a local secret file. If a tool absolutely requires `.env.local`, generate it locally, keep it ignored, and treat it as disposable cache rather than a source of truth.

## Repository rules for secrets

Every application repository should follow these rules:

- Commit `.env.example` with variable names and safe example/placeholder values only.
- Ignore `.env`, `.env.local`, `.env.*.local`, and other files containing real values.
- Never put secrets in source code, fixtures, screenshots, issues, PR bodies, comments, logs, traces, prompts, or documentation.
- Never expose secrets through `NEXT_PUBLIC_*`. Anything with a `NEXT_PUBLIC_` prefix must be treated as public client-side configuration.
- Redact authentication headers, tokens, cookies, connection strings, and sensitive payloads from logs and observability.
- Give each environment only the permissions it needs.
- Rotate a secret immediately if it is accidentally exposed; deleting the commit or message is not enough.

## Vercel

Use Vercel for frontend deployment and Preview Deployments.

For user-managed secrets, prefer an Infisical -> Vercel Secret Sync rather than manually maintaining the same values in both systems.

Map environments deliberately:

```text
Infisical dev      -> local development
Infisical preview  -> Vercel Preview
Infisical prod     -> Vercel Production
```

Do not put backend-only credentials into the frontend project unless the server-side Next.js runtime genuinely needs them.

## Railway

Use Railway for backend services, workers, jobs, and managed PostgreSQL when appropriate.

For user-managed secrets, prefer an Infisical -> Railway Secret Sync. Keep Railway-owned reference variables and platform-generated database/service values in Railway.

Use service-scoped variables when only one service needs a secret. Use shared variables only for values genuinely shared by multiple services.

Backend services should expose a health endpoint. Database migrations should run as an explicit deployment step before the new application version receives normal traffic when the project uses migrations.

## GitHub Actions and CI

Do not create long-lived GitHub Secrets merely to authenticate to Infisical when OIDC is available.

Preferred pattern:

```text
GitHub Actions
  -> GitHub OIDC short-lived identity token
  -> Infisical machine identity
  -> only the required environment/path secrets
  -> job environment
```

Scope CI identities to the specific repository, workflow/environment, and minimum secret paths they require.

Production CI access is separate from development access. A build/test workflow should not automatically gain production secrets just because it runs on GitHub.

## Human credentials

Infisical stores application secrets; it does not remove the need to protect the human accounts used to reach GitHub, Infisical, Vercel, Railway, OpenAI, and other providers.

Store those account credentials, passkeys, 2FA recovery information, and recovery codes in a trusted password manager that synchronizes across the user's devices. Prefer passkeys or hardware-backed MFA where supported.

Do not store human account passwords or recovery codes in project repositories or project secret folders.

## Production access

Production secrets are operational credentials, not normal development context.

- Coding agents must not read, print, copy, rotate, or modify production secret values unless the user explicitly authorizes that specific production action.
- Local development should use `dev` by default.
- CI should use short-lived workload identity and least privilege.
- Vercel/Railway should receive only the secrets required by the service being deployed.
- Production secret changes should be auditable and followed by a redeploy/restart only when the affected runtime requires it.

## New-project checklist

For each new application/template:

1. GitHub repository created; `main` is the production branch.
2. `.env.example` exists and real `.env*` values are ignored.
3. Infisical project exists with `dev`, `preview`, and `prod` as needed.
4. `.infisical.json` is committed when the project uses the CLI.
5. Local start commands can run through `infisical run`.
6. Next.js frontend is connected to Vercel when present.
7. FastAPI/worker/database services are connected to Railway when present.
8. User-managed Vercel/Railway secrets are synced from Infisical instead of copied manually where supported.
9. CI uses OIDC/machine identity for secret access where supported.
10. Preview/production credentials are separated and production access is least-privilege.
11. Health and smoke checks cover the smallest critical end-to-end path after deployment.

Keep this setup boring. Add staging, extra vault layers, custom deployment tooling, or additional secret stores only when a concrete requirement justifies them.
